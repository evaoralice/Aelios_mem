# Aelios 缓存与记忆系统改造方案

> 基于现有项目改造，不重建。

---

## 一、改造目标

在现有 Aelios 架构上调整缓存结构和记忆流程，使其更贴合实际使用场景：
- 缓存结构更合理，覆盖更多稳定内容
- 记忆注入方式从追加文本改为伪造 tool call，语义更自然
- 模型可以在对话中主动存记忆
- 每日总结更详细，保留历史日志
- 动态时间信息合并到记忆 tool call 中

---

## 二、改造后的 prompt 结构

```
[断点1: 工具列表末尾]
  客户端工具定义（含 MCP 注入的工具）

[断点2: 系统锚点]
  固定提示词（proxy_static_rules）
  珍贵记忆（precious）
  输出风格（preset_lite）
  前端设定（client_system）                    ← 缓存锚点

  ---- 以下不走断点2缓存，但走断点3缓存 ----
  长期画像摘要（digest，≤1000字）
  最近两天日志（分条列点，每天≤800字）
  术语表（glossary）

[断点3: 术语表之后]                             ← 新增断点位置

  ---- 以下完全不缓存 ----

[对话历史]
  ...历史消息...

[断点4: tail — 倒数第二条消息]

[用户最新消息]

[伪造 tool call: memory_context]
  assistant: tool_use → memory_context(query="...")
  user: tool_result → [2026-07-11T15:30:00+08:00]
                       memory1: 用户喜欢在凌晨工作
                       memory2: 之前讨论过缓存分层设计
                       ...
```

### 与现有结构的变化点

| 项目 | 现在 | 改成 |
|------|------|------|
| 记忆注入方式 | 追加到最后一条 user 消息末尾 | 伪造一轮 tool call |
| 记忆注入位置 | user 消息内部 | 用户消息之后，模型回复之前 |
| 动态时间信息 | 单独的 client_volatile_context 块 | 合并到 tool_result 的 timestamp 中 |
| 断点3位置 | 不存在（bridge 在历史中段） | 术语表之后（新增） |
| bridge 断点 | 历史中段 | 移除，由新断点3替代 |
| digest 长度 | ≤500字 | ≤1000字 |
| 昨日日志 | 一句话，只保留一天 | 分条列点≤800字，保留所有历史，注入最近两天 |

## 三、分阶段实施计划

### 阶段 1：记忆日志改造（低风险）

**改动内容：**
- 做梦 prompt 改为输出分条列点总结（≤800字，高信息密度，按给模型看的方式写）
- `daily_log` 表改为每天新增一行（不覆盖历史日志）
- `formatBootStable` 改为查最近两天日志拼接注入
- digest 上限从 500 改为 1000 字
- 做梦 cron 从 UTC 20:10（北京 04:10）改到 UTC 19:00（北京 03:00），避免 8:00-12:00 消息遗漏

**涉及文件：**
- `src/memory/dailyDigest.ts` — 做梦 prompt + 日志写入逻辑
- `src/db/v2.ts` — daily_log 的 upsert 改为 insert
- `src/assembler/types.ts` — `formatBootStable` 查两天日志
- `wrangler.toml` — cron 时间
- `src/index.ts` — cron 常量

**验证：**
- 手动触发做梦，检查日志输出格式
- 确认旧日志不被覆盖
- `node scripts/verify-assembler.mjs`

---

### 阶段 2：记忆来源标记 + 召回加权（低风险）

**改动内容：**
- 所有写入路径标记 source 字段：
  - MCP 手动写入 → `"mcp"`（已有）
  - 模型自存 → `"model"`（阶段3实现后）
  - 提取管线 → `"extract"`
  - 做梦 → `"dream"`
- 召回排序时，`source` 为 `"model"` 或 `"mcp"` 的记忆得分 × 1.2
- 加权幅度适当，不压过相关性，只在相关性接近时起作用

**涉及文件：**
- `src/memory/extractPipeline.ts` — 标记 source = "extract"
- `src/memory/dailyDigest.ts` — 标记 source = "dream"
- `src/memory/v2/recall.ts` — 召回排序加权逻辑
- `src/db/v2.ts` — 确认 source 字段写入

**验证：**
- 通过 MCP 写入记忆，确认 source 标记
- 搜索记忆，确认加权后排序变化

---

### 阶段 3：注入 memory_save 工具定义（中风险）

**改动内容：**
- proxy 在发给 Claude 的 tools 列表里注入 `memory_save` 工具定义
- 工具说明写清楚：用于在对话中记录值得长期保存的信息
- 参数：content（必填）、type（可选，列出9种类型）、importance（可选）
- proxy 本身不拦截 tool_use —— Claude 返回 tool_use 后，客户端通过 MCP 连接执行
- 客户端需要能把 `memory_save` 的 tool_use 映射到 MCP 的 `memory_upsert`

**涉及文件：**
- `src/proxy/anthropicAdapter.ts` — 注入工具定义
- `src/assembler/toAnthropic.ts` — 确认注入的工具参与排序和缓存

**验证：**
- 发送不带 tools 的请求，确认 memory_save 被自动注入
- 发送带 tools 的请求，确认 memory_save 和客户端工具共存
- 模型返回 tool_use: memory_save 后，客户端能正确执行

**待确认：**
- 客户端是否能自动将 tool_use 名称映射到 MCP 工具名称
- 如果不能，可能需要 proxy 拦截并直接执行（备选方案）

---

### 阶段 4：伪造 tool call 注入记忆（高风险）

**改动内容：**
- 定义 `memory_context` 伪工具：
  - 说明：用于传递长期记忆的伪工具，非实际可调用工具，模型不应主动调用此工具
  - 注入到 tools 列表中
- 扩展 assembler 支持合成 tool_use + tool_result 消息对
- 把 `dynamic_memory_patch` 从"追加到 user 消息文本"改为：
  - 在用户最新消息之后插入一轮伪造 tool call
  - assistant 消息：tool_use → memory_context
  - user 消息：tool_result → `[timestamp] memory1:..., memory2:...`
- 记忆格式参考现有的 `<memories>` 标签格式，加上时间戳
- 移除 `client_volatile_context` 块（时间信息合并到 tool_result）

**涉及文件：**
- `src/assembler/types.ts` — 扩展 AssembledMessage 类型支持 tool_calls
- `src/assembler/blocks.ts` — 修改 dynamic_memory_patch 输出
- `src/assembler/assemble.ts` — 构造合成 tool call 消息对
- `src/assembler/toAnthropic.ts` — 处理合成 tool_use/tool_result 块
- `src/assembler/toOpenAI.ts` — 同步处理（如果需要支持 OpenAI 兼容模型）
- `src/proxy/anthropicAdapter.ts` — 移除 splitDynamicMemorySystemBlock + appendUncachedUserContext 逻辑

**验证：**
- `node scripts/verify-cache-strategy.mjs` — 确认断点数 ≤4
- `node scripts/verify-assembler.mjs`
- 实际对话测试，确认模型能正确读取 tool_result 中的记忆
- 确认模型不会尝试主动调用 memory_context

---

### 阶段 5：缓存断点调整（中风险，与阶段4同步）

**改动内容：**
- 断点3 从历史中段 bridge 改为术语表之后
- 确认断点总数 ≤4（Anthropic 限制）：
  1. 工具列表末尾
  2. client_system（系统锚点）
  3. 术语表之后（新）
  4. tail（倒数第二条消息）
- 摘要 + 两天日志 + 术语表进入断点2-3之间的缓存区域

**涉及文件：**
- `src/proxy/anthropicAdapter.ts` — 断点计算逻辑
- `src/assembler/types.ts` — 块顺序定义

**验证：**
- `node scripts/verify-cache-strategy.mjs`
- 实际请求，通过 `/v1/debug/cache_health` 确认缓存命中率

## 五、不在本次改造范围内

| 项目 | 原因 |
|------|------|
| 多窗口隔离 | 暂不考虑，当前单窗口场景足够 |
| 完整消息历史存储 | 优先级低，用客户端本地保留 |
| 缓存心跳机制 | 等实际测试结构后再决定 |
| 自动提取管线 | v2 模式下已禁用，保持现状 |

---

## 六、风险评估

| 阶段 | 风险 | 回退方案 |
|------|------|---------|
| 1 日志改造 | 低 — 只改输出格式和存储方式 | 还原做梦 prompt 和 upsert 逻辑 |
| 2 来源加权 | 低 — 加权系数可调 | 把系数改回 1.0 |
| 3 注入工具 | 中 — 依赖客户端 MCP 映射 | 不注入，走手动 MCP |
| 4 伪造 tool call | 高 — 改动 assembler 核心 | 保留原有的文本追加方式作为 fallback |
| 5 缓存断点 | 中 — 需要验证命中率 | 还原到原有断点位置 |

---

## 七、实施顺序建议

```
阶段1（日志） → 阶段2（来源加权） → 阶段5（缓存断点） → 阶段3（工具注入） → 阶段4（伪造tool call）
```

建议先做 1 和 2，验证稳定后再动缓存和 assembler。阶段 4 和 5 建议一起做，因为伪造 tool call 和缓存断点调整互相关联。
