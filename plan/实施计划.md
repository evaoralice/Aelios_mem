> 基于《缓存与记忆改造方案.md》对照现有代码整理的执行细则。

## 现有架构概览

```
写入侧                              读取侧                            组装侧
extractPipeline (4h cron)  ──┐     buildBootPackage  ──────────→    boot_stable block
dailyDigest    (daily cron) ──┼──→  D1 + Vectorize  ──→            (after anchor, day-stable)
MCP upsert               ──┘     runRecall (per-turn) ────────→     dynamic_memory_patch
                                                                  (after anchor, uncached)
```

- 缓存 anchor 在 `client_system` 之后
- `boot_stable`（digest + 日志 + glossary）在 anchor 之后，天级稳定
- `dynamic_memory_patch`（召回结果）在所有断点之后，完全不缓存
- `client_volatile_context`（时间等动态信息）单独剥离，不缓存

当前 4 断点：工具列表末尾 / 系统锚点 / bridge（历史中段） / tail（倒数第二条消息）

## 阶段 1：日志改造（低风险）

### 目标

| 项目 | 现状 | 改成 |
|------|------|------|
| 做梦输出 | JSON 操作指令 | 追加分条列点日志（≤800字） |
| daily_log 存储 | upsert(同日覆盖) | 保留唯一约束，不同日期新增（现状已满足） |
| boot 注入 | 只读一天日志 | 读最近两天拼接 |
| digest 上限 | ≤500字 | ≤1000字 |
| 做梦 cron | UTC 20:10(北京04:10) | UTC 19:00(北京03:00) |

### 涉及文件与改动

**`src/memory/dailyDigest.ts`**

- `buildDigestPrompt`(:427)：prompt 追加要求输出分条列点日志段落，≤800字，高信息密度，按给模型看的方式写。
- 做梦 prompt 里有 digest 截断 ≤500字的指令 → 改为 ≤1000字。
- `applyDreamV2`(:719)：写入记忆时传 `source: "dream"`（阶段2同时改）。写入 daily_log 保持现有 upsert 即可（`(namespace, date)` 唯一约束，同日覆盖、不同日期新增，已满足保留历史需求）。

**`src/db/v2.ts`**

- `upsertDailyLog`(:992): 现状是 `ON CONFLICT(namespace, date) DO UPDATE`，**保留不动**。每天一行，不同日期不覆盖。
- **新增** `getRecentDailyLogs` 函数:
  ```sql
  SELECT * FROM daily_log
  WHERE namespace = ?
  ORDER BY date DESC
  LIMIT ?
  ```

**`src/assembler/types.ts`**

- `formatBootStable`(:156):
  ```typescript
  // 现状
  <digest>...</digest>
  <yesterday_log>...</yesterday_log>
  <glossary>...</glossary>

  // 改成
  <digest>...</digest>           (≤1000字)
  <daily_log>
    [2026-07-10] - 条目1 / 条目2 / 条目3
    [2026-07-09] - 条目1 / 条目2 / 条目3
  </daily_log>
  <glossary>...</glossary>
  ```

**`src/memory/v2/recall.ts`**

- `buildBootPackage`(:150): 从 `getDailyLog`(单条)改为 `getRecentDailyLogs`(两天):
  ```typescript
  // 现状
  const dailyLog = await getDailyLog(env, namespace);

  // 改成
  const recentLogs = await getRecentDailyLogs(env, namespace, 2);
  ```
- **时区注意:** `buildBootPackage` 计算昨天日期用的是 `Asia/Singapore` 时区(`Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Singapore" })`)。算前天日期**必须用同样的时区逻辑**，不能用 UTC 算，否则跨天边界会出错。
- `BootPackage` 类型(:139): `yesterday_log: string` → `recent_logs: { date: string; content: string }[]`
- `formatBootStable` 配合改，接收新字段并按日期分条渲染。

**`src/api/mcp.ts`**

- `digest_set` 工具里有截断逻辑(≤500字) → 改为 ≤1000字。审查意见指出这是容易遗漏的第二处截断点。

**`wrangler.toml`**

- `[triggers] crons` 第二条 `"10 20 * * *"` → `"0 19 * * *"`

**`src/index.ts`**

- `DAILY_MAINTENANCE_CRON` 常量同步改。

### 实际需要改的只有两处

**`src/memory/dailyDigest.ts`**

- `applyDreamV2`(:719)：确认写入记忆时是否传了 source。如果为空，补传 `source: "dream"`。

**`src/memory/v2/recall.ts`**

- `runRecall`(:268): 在 `filterAndCompressMemories`(reranker + LLM 压缩)之后、gate-2 去重之前，对 source 为 `"model"` 或 `"mcp"` 的命中得分 × 1.2:
  ```typescript
  const boost = parseFloat(env.RECALL_SOURCE_BOOST ?? "1.0");
  const weightedHits = hits.map(hit => {
    if (boost > 1 && (hit.source === "model" || hit.source === "mcp")) {
      return { ...hit, score: hit.score * boost };
    }
    return hit;
  });
  weightedHits.sort((a, b) => b.score - a.score);
  ```

- **加权位置很重要:** 必须在 reranker 评分之后、gate-2 的 Jaccard 去重之前。

## 阶段 3：明确 memory_upsert 的 fact_key 说明（低风险）

### 背景

MCP 已有 `memory_upsert` 工具，模型可以直接调用来主动存/更新记忆。**不需要新建 `memory_save` 包装工具。**

阶段 3 只需优化 `memory_upsert` 的 description，让模型更清楚 `fact_key` 的用途，从而在对话中正确调用。

### fact_key 是什么

`fact_key` 是记忆的**业务唯一键**，用于判断"两条记忆是否描述同一事实"：

```
第一次存: fact_key = "user_work_schedule", content = "用户喜欢凌晨工作"
几天后更新: fact_key = "user_work_schedule", content = "用户改成了早起"
→ upsert 命中同一 key，更新内容，不产生重复
```

没有 `fact_key` 的话，每条记忆互相独立，去重只能靠向量相似度（0.9 阈值），远不如 key 精确。

### 涉及文件与改动

**`src/api/mcp.ts`** — `memory_upsert` 工具定义（:258）

当前 description:
```
"Assert/update a refined memory by fact_key (no waiting for dream). ..."
```

改为:
```typescript

  description:
    "Assert/update a refined memory by fact_key (no waiting for dream). " +
    "Use this proactively during conversation when the user reveals lasting facts, preferences, or relationship details. " +
    "world_fact also uses this with type='world_fact'. " +
    "Available types: fact, event, preference, relationship, boundary, habit, decision, note, world_fact. Defaults to 'fact'.",
  inputSchema: {
    type: "object",
    properties: {
      fact_key: {
        type: "string",
        description:
          "Stable business key for deduplication. Reusing the same fact_key updates existing memory instead of creating a duplicate. " +
          "Examples: 'user_work_schedule', 'user_food_preference', 'relationship_with_alice'. " +
          "Choose a concise, descriptive key that represents this fact."
      },
      content: { type: "string" },
      type: { type: "string", description: "Memory type. One of: fact, event, preference, relationship, boundary, habit, decision, note, world_fact. Defaults to 'fact'." },
      importance: { type: "number" },
      confidence: { type: "number" },
      tags: { type: "array", items: { type: "string" } },
      source: { type: "string" },
```

## 阶段 4：伪造 tool call 注入记忆（高风险）

### 目标

把 `dynamic_memory_patch` 从"追加到 user 消息文本末尾"改为"在用户最新消息之后插入一轮伪造 tool call"。

### 改前流程

```
assemble() → system_blocks[dynamic_memory_patch] = "<memories>...</memories>"
           → messages[...history, currentUser]
anthropicAdapter.appendUncachedUserContext() →
  dynamic_memory_patch 文本追加到最后一条 user 消息后面
```

### 改后流程

```
assemble() → system_blocks(不含 dynamic_memory_patch)
           → messages[...history, currentUser,
                       synthetic_assistant: { tool_use → memory_context },
                       synthetic_user: { tool_result → [timestamp] memory1, memory2, ... }
                      ]
```

### memory_context 工具定义方案（审查意见调整）

**`memory_context` 工具定义放在 MCP 里提供，不由 proxy 注入。**

理由:
- 从模型视角看，MCP 提供和 proxy 注入没有区别——tools 列表是合并的
- 放 MCP 里管理更统一，不需要 proxy 注入逻辑
- 以后可以给 `memory_context` 加真正的执行逻辑(调 `runRecall`)，作为注入失败时的 fallback
- 工具描述标注"系统专用"即可，模型大概率不会主动调用(已经从 tool_result 拿到记忆了)

同时在系统提示词或术语表里补充说明:
- `memory_context` 是系统自动调用的记忆注入工具
- tool_result 中的内容是系统根据当前对话召回的相关长期记忆
- 模型直接参考内容即可，无需主动调用

## 阶段 5：缓存断点调整（中风险，与阶段 4 同步）

### 目标

断点 3 从"bridge(历史中段)"改为"术语表之后(boot_stable 末尾)"。

### 当前 4 断点

1. 工具列表末尾
2. 系统锚点(`client_system` 之后)
3. Bridge(历史中段，当 `blocksBeforeTail > 16` 时)
4. Tail(倒数第二条消息)

### 改后 4 断点

1. 工具列表末尾
2. 系统锚点(`client_system` 之后)
3. `boot_stable` 末尾 ← 替换 bridge
4. Tail(倒数第二条消息)

### 关于移除 bridge 的影响（审查意见修正）

审查意见指出原计划**过于保守**。实际上:

- tail 断点已经覆盖了到倒数第二条消息为止的所有历史
- bridge 是"双保险"，实际触发场景有限
- 把 bridge 换成 boot_stable 断点，让摘要+日志+术语表被缓存，**整体是赚的**
- 长对话缓存效率不会明显下降

如果后续实测发现长对话(50+ 轮)缓存命中率确实下降，再考虑调整。

### `verify-cache-strategy.mjs` 更新

- T7/T8(bridge 出现/消失条件) → 改为检查断点 3 在 boot_stable 位置
- T13(≤4 断点)仍然有效
- T11(glossary 变化不影响缓存前缀) → 需要重新评估: glossary 在 boot_stable 内，glossary 变化现在会让断点 3 缓存失效。测试仍应通过(因为断点 2 锚点不变)。

## 实施顺序与依赖

```
阶段1（日志）       ──→ 可独立上线
阶段2（来源加权）    ──→ 可独立上线（source 列已确认存在）
阶段3（fact_key 说明）    ──→ 可独立上线（仅改 MCP 工具描述）
阶段5（缓存断点）   ──┐
                     ├──→ 阶段 4 和 5 必须一起做
阶段4（伪造tool call）──┘
```

**建议顺序: 1 → 2 → 3 → (4+5)**

阶段 3 现已简化为仅优化 MCP 工具描述，风险降为低。排在 4+5 之前仍然是合理的——先确认模型能正确主动调用 `memory_upsert`，再动 assembler 核心逻辑。

## 风险与回退

| 阶段 | 风险 | 回退方案 |
|------|------|---------|
| 1 日志 | 低 — 只改输出格式和查询 | 还原 prompt 和查询逻辑 |
| 2 来源加权 | 低 — 系数可调 | `RECALL_SOURCE_BOOST=1.0` |
| 3 fact_key 说明 | 低 — 只改 description | 还原 description |
| 4 伪造 tool call | 高 — 改动 assembler 核心 | `MEMORY_INJECTION_MODE=text` 切回文本追加 |
| 5 缓存断点 | 中 — 需验证命中率 | 还原 bridge 断点逻辑 |

阶段 4 保留 `appendUncachedUserContext` 函数不删，通过环境变量切换，是最高风险阶段的安全网。
