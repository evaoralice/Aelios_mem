# 实施计划审查意见

> 对《实施计划.md》的代码级审查，供执行模型参考修改。

---

## 总体结论

方案整体可行，代码分析准确。以下是需要注意和修正的点。

---

## 阶段 1：日志改造

### 准确的部分
- `upsertDailyLog` 确实是 `ON CONFLICT(namespace, date) DO UPDATE`，保留唯一约束的建议正确
- `buildBootPackage` 只读昨天一条日志，改为读两天的方向正确
- `BootPackage` 类型改动方向正确

### 需要补充
1. **时区问题：** `buildBootPackage` 里计算"昨天日期"用的是 `Asia/Singapore` 时区（`Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Singapore" })`）。算前天日期时必须用同样的时区逻辑，不要用 UTC 算
2. **digest 截断有两处要改：**
   - `dailyDigest.ts` 的做梦 prompt 里（指示模型输出 ≤500 字 → 改 ≤1000 字）
   - MCP 的 `digest_set` 工具里有截断逻辑（≤500 字 → 改 ≤1000 字）
3. **新增函数：** 需要在 `db/v2.ts` 新增 `getRecentDailyLogs`，SQL 为 `SELECT * FROM daily_log WHERE namespace = ? ORDER BY date DESC LIMIT ?`

## 阶段 2：来源标记 + 召回加权

### 修正
- **`extractPipeline.ts` 不需要改。** 它已经在所有 4 条写入路径传了 `source: "extract"`。计划里把这列为改动项是多余的
- **`memories` 表已有 `source` 列，不需要 migration。** 计划里的"前提确认"已解答

### 实际需要改的只有两处
1. `src/memory/dailyDigest.ts` — 做梦写入记忆时标记 `source: "dream"`（确认当前是否传了 source，可能为空）
2. `src/memory/v2/recall.ts` — 新增加权逻辑（代码示例正确）

---

## 阶段 3：注入 memory_save 工具定义

### 需要修正
1. **注入位置应提前到 `chatCompletions.ts` 层**（在 `body.tools` 上直接追加），而不是在 `anthropicAdapter.ts` 里。这样不管走 Anthropic 还是 OpenAI 兼容路由都能注入
2. **`type` 的 enum 应与管理面板的 8 个 tab + world_fact 对齐：** `fact, event, preference, relationship, boundary, habit, decision, note, world_fact`。计划里列的 `identity, persona` 等不在面板 tab 里，模型存了这些类型在面板上看不到

---

## 阶段 4：伪造 tool call 注入记忆

### memory_context 工具定义的方案调整

**`memory_context` 工具定义放在 MCP 里提供，不由 proxy 注入。**

理由：
- 从模型视角看，MCP 提供和 proxy 注入没有区别——tools 列表是合并的
- 放 MCP 里管理更统一，不需要 proxy 注入逻辑
- 以后可以给 `memory_context` 加真正的执行逻辑（调 `runRecall`），作为注入失败时的 fallback
- 工具描述标注"系统专用"即可，模型大概率不会主动调用（已经从 tool_result 拿到记忆了）

同时在系统提示词或术语表里补充说明：
- `memory_context` 是系统自动调用的记忆注入工具
- tool_result 中的内容是系统根据当前对话召回的相关长期记忆
- 模型直接参考内容即可，无需主动调用

### tool_use_id 确定性问题

计划里担心"每轮 ID 变化导致字节变化影响缓存"——**这个担心是多余的。** 伪造的 tool call 在所有缓存断点之后（用户最新消息之后），不影响任何缓存前缀。用随机 ID 也没问题。

### 其他部分
- Fallback 机制（`MEMORY_INJECTION_MODE=text|toolcall`）设计合理
- 保留 `appendUncachedUserContext` 不删的建议正确
- tail 断点需要排除合成消息的逻辑正确

---

## 阶段 5：缓存断点调整

### 关于移除 bridge 的影响

计划第 457-459 行的担心**过于保守**。实际上：

- tail 断点已经覆盖了到倒数第二条消息为止的所有历史
- bridge 是"双保险"，实际触发场景有限
- 把 bridge 换成 boot_stable 断点，让摘要+日志+术语表被缓存，**整体是赚的**
- 长对话缓存效率不会明显下降

如果后续实测发现长对话（50+ 轮）缓存命中率确实下降，再考虑调整。

---

## 实施顺序建议

计划建议 `1 → 2 → (4+5) → 3`

**建议调整为：`1 → 2 → 3 → (4+5)`**

理由：阶段 3 比 4+5 简单得多，可以提前验证客户端的 MCP 工具映射能力。如果客户端映射不了 `memory_save`，需要改成 proxy 拦截方案，这会影响阶段 4 的设计。先做 3 能提前排雷。
