## 使用场景约定（方案依据，改动不得违背）

1. 前端保留上一窗口五轮对话 + 当前消息一起发，网关补充召回记忆。
2. 记忆与长期记忆修改主要走 MCP；**对外暴露的删除一律软删**（数据是资产，不可静默丢失）。
3. 召回记忆、长期记忆更新**不得破坏缓存前缀**（pending 白天挂账、做梦夜里合并的设计保持）。
4. 四维（emotional/recurrence/unresolved/weight）**现阶段只记录不消费**，先积累干净数据，之后再定召回时的使用方式。
5. 召回要准确；MCP 主动记入置信度高，有 source 权重加成（已有，保持）。
6. 角色记忆**允许互相召回**（防角色下架后记忆孤岛），但当前角色有加成（roleBoost，已有，保持）。
7. `ROLE_MEMORY_ENABLED=true`（线上确认）。
8. 缓存命中尽可能保持。

**明确不改的"伪问题"**（按场景重新定性为特性）：
- 召回不按 role_scope 过滤 → 特性（需求 6）。
- pending 跨请求重复注入直到 applied → 有意设计（防模型重复提交）。
- baseline 每晚合并使断点 3 日更失效一次 → 可接受成本。

  受影响调用链：`db/v2.ts syncMemoryVector`（upsertMemoryByFactKey / supersedeMemory）。

### P0-2 ✅ 四维数据保真（记录期数据被污染）

两个子问题，都不改"使用方式"，只保证记录的数据干净：

**(a) `updateVectorMemory` 清零三维+weight**
- **文件**：`src/memory/vectorStore.ts:497-560` + `vectorMetadataToMemoryRecord`（:136 附近）
- **问题**：向量 metadata 没存四维，`vectorMetadataToMemoryRecord` 硬编码 0；
  `updateVectorMemory` 用 `existing.emotional ?? 0` 写回 D1 → 原有维度值被覆写为 0。
  importance 变更时 weight 也不重算（对比 `db/memories.ts updateMemory` 会重算）。
- **修改范围**：更新路径改为从 D1 读旧维度值（或 metadata 补存四维），
  weight 按 `computeWeight` 重算。

**(b) extract 管线不产出三维**
- **文件**：`src/memory/extractPipeline.ts:166-180`（`normalizeCandidate`）+ 提取 prompt
- **问题**：提取 prompt 不要求输出三维，normalize 也不解析 → extract 写入的记忆
  weight 上限 0.35，dream 更新过的可达 1.0，同表两套量纲，之后无法分析。
- **修改范围**：提取 prompt JSON 示例补三维字段（对齐 dailyDigest.ts:355 的 dream prompt），
  `normalizeCandidate` 解析 + 透传到 upsert/create/supersede 调用。
- **验证**：`node scripts/verify-extract-pipeline.mjs` + `npx tsc --noEmit`。

### P0-3 ✅ retention 硬删违背软删方针 + 侧车孤儿行

- **文件**：`src/memory/retention.ts:112-150` + `src/db/retention.ts:158-172`
- **问题**：
  - cron 对 365 天前终态记忆无条件**硬删**（`hardDeleteMemoriesBatch`），
    与"对外全软删"方针矛盾——外面软删保下来的数据一年后被后台悄悄物理删除；
  - `MEMORY_AUTO_DELETE` / `MEMORY_PATROL_DRY_RUN`（types.ts:31-33）声明了但零引用，
    "保险闸"是假的；
  - 硬删只删 `memories` 不删 `memory_lifecycle` 侧车行（对比 `deleteMemoryV2` 会删），
    侧车表无限膨胀。
- **修改范围**：
  1. 实现 `MEMORY_AUTO_DELETE` 闸门：默认 false 时跳过硬删（只 log 候选数）；
  2. 保留硬删代码路径供显式开启，开启时同步清理 `memory_lifecycle`；
  3. 顺手修 `retention.ts:112` 注释（写 30 天实为 365 天）。
- **验证**：`node scripts/verify-assembler.mjs`（镜像常量）+ 相关单测。

### P0-4 ✅ 活跃记忆 180 天必过期（retention 与 recall 矛盾）

- **文件**：`src/db/retention.ts:84-123`（`expireOldMemories`）
- **问题**：过期条件只看 `updated_at < 180 天`；召回/注入只写
  `last_recalled_at` / lifecycle 侧车，不碰 `updated_at`。
  天天被召回的高价值记忆 180 天没被"编辑"就 expired 且删向量（召回层面死亡）。
- **修改范围**：过期 SQL 加条件 `AND (last_recalled_at IS NULL OR last_recalled_at < 阈值)`，
  阈值复用 180 天常量（更新过 or 被召回过，二者有一即续命）。
- **验证**：`npx vitest run` + 手工核 SQL。

## P1 — 缓存命中（需求 3/8）

### P1-5 ✅ client_volatile_context 时间行拖垮 tail 断点

- **文件**：`src/assembler/blocks.ts:310-325`（块内容）、`blocks.ts:563-575`（tail 断点）、
  `src/proxy/anthropicAdapter.ts`
- **问题**：代码已把 `dynamic_memory_patch` 拆出 system 移到消息尾保护缓存，
  但 `client_volatile_context`（分钟级时间/日期行）仍是 system 块，
  处于消息级 tail 断点（断点 4）的前缀内 → 时间一变断点 4 必 miss，
  且每次产生 cache_creation 写入成本。实际只有断点 1-3 生效。
  前端带五轮历史，历史前缀本身稳定，这部分收益现在完全吃不到。
- **方案**（二选一，动手前定）：
  - a) 时间粒度降级：块内时间只保留到小时（或半天），断点 4 在粒度窗口内可命中；
  - b) 把 volatile 块移出 system，并入消息尾的 dynamic_memory_patch 注入
    （断点之后，彻底不污染前缀）。
  - 倾向 **b**（一劳永逸，且 plan/遗留待解决问题.md 第 1 条早有此意）；
    若 b 改动/测试面过大再退到 a。
- **验证**：`node scripts/verify-cache-strategy.mjs` + `npx vitest run test/assembler/`。
- **注**：`blocks.ts:515` / `anthropicAdapter.ts:634` 注释与实际锚点不符
  （说 persona_pinned，实为 client_system；说 boot_stable 不缓存，实际断点 3 缓存它），
  改这块时顺手修正注释。

### P1-6 ✅ tail 断点 block_index 在多模态/合并消息下错位

- **文件**：`src/assembler/blocks.ts:556-575`（计算）vs
  `src/assembler/toAnthropic.ts:214-233, 376-381`（应用）
- **问题**：断点 block_index 按组装后消息算，但 `contentToPlainText` 把多模态
  content 数组 stringify 成单个 text block → index 指向 undefined，断点静默丢弃；
  连续同 role 消息合并同理；tail 落在 tool_result 块上也不打标。
- **修改范围**：断点应用改为"最后一条消息的最后一个可打标块"这类结构化定位，
  不依赖预先算好的 index；或在 toAnthropic 转换后重算 index。
- **验证**：`node scripts/verify-cache-strategy.mjs` + 补多模态/tool 轮次用例。

## P2 — 召回准确性（需求 5）

### P2-7 ✅ filter 故障时兜底注入 longtail（回收站内容）

- **文件**：`src/memory/v2/recall.ts:508` + `src/memory/filter.ts:595-667`
- **问题**：压缩模型出错且 fail-closed 时 `filterAndCompressMemories` 返回 `[]` →
  recall 空 → 落 longtail 兜底（被删记忆的遗物）。模型故障时用户拿到的
  不是"没有记忆"而是回收站内容，与"召回要准确"矛盾。
- **修改范围**：区分"过滤后确实为空"和"过滤失败"两种空——
  失败时直接返回空结果，不触发 longtail 兜底（宁缺毋滥）。
- **验证**：filter 相关单测 + 补一个 fail-closed 场景用例。

### P2-8 ✅ extract 管线角色归属粗糙 + 查重不分角色

- **文件**：`src/memory/extractPipeline.ts:474-476`（role 取值）、
  `:270-296`（`findEmbeddingDuplicate`）
- **问题**：
  - 4h 窗口内所有提取记忆归到**最后一条 user 消息**的角色，多角色混聊窗口归属错乱
    （dream 有按 scope 分组，extract 没有）；
  - embedding 查重的 Vectorize filter 不含 role → 角色 A 的新记忆可能因与
    shared/角色 B 的记忆相似而被 markSeen 丢弃。
- **修改范围**：
  1. 提取时按消息的 role_id 分组，各组独立提取归属（对齐 dream 的做法）；
  2. `findEmbeddingDuplicate` 查重命中后校验 role_scope 一致才算重复
    （注意：跨角色召回是特性，但**写入判重**必须分角色，二者不冲突）。
- **验证**：`node scripts/verify-extract-pipeline.mjs` + `npx vitest run test/multirole/`。
