## 1. client_volatile_context 可能导致 recent_history 缓存失效

**状态：** 待验证

**问题：**

`client_volatile_context` 是独立 system block，排在 `recent_history` 之前。如果前端在 system 消息里传了时间/日期，会被自动拆分到这个 block。由于 system blocks 顺序排列，前面的 block 内容变化会导致后面的 message-level breakpoint 缓存失效，可能让全部历史记录缓存失效。

**当前行为：**

- `splitClientSystemTexts` 只拆 system 消息，不拆 user/assistant 消息
- 拆出的时间/日期行放入 `client_volatile_context` block（dynamic，不缓存）
- 如果前端不在 system 消息里传时间（而是放在 user 消息里），则不会触发拆分，不影响缓存

**待验证：**

实际使用时，测试前端注入的时间信息是否会被拆出来：
- 如果不拆（时间在 user 消息里）→ 不影响缓存，无需处理
- 如果拆了（时间在 system 消息里）→ 需要处理

**潜在方案（如果需要处理）：**

把 `client_volatile_context` 从独立 system block 移到 toolcall 模式的 `memory_context` 伪造 tool_result 里，和召回记忆 + pending 一起注入。这样它不再是 system block，不影响后面的 history 缓存。

注入顺序建议：
```
[timestamp]
=== 当前上下文 ===
当前时间：2025-07-22 20:30
=== 召回记忆 ===
<memories>...</memories>
=== 待处理变更（今日）===
...
```

**注意：**

- `MEMORY_INJECTION_MODE=text` 时怎么处理需另议（当前 text 模式追加到 user 消息）
- 移走后 recent_history 前面少一个 system block，message-level breakpoint 的 20-block lookback 间距可能变化，需确认
- `MEMORY_INJECTION_MODE` 只管 RAG + pending，不管 volatile context，需要扩展控制范围

**相关文件：**

- `src/assembler/blocks.ts` — `clientVolatileContextBlock`（287-307 行）、`splitClientSystemTexts`（235-272 行）
- `src/proxy/anthropicAdapter.ts` — `buildSyntheticContext`（234-262 行）
- `src/assembler/types.ts` — `BLOCK_ORDER`（140-151 行）

## 2. 召回记忆注入不带 role_scope 标签

**状态：** 待定，影响小

**问题：**

RAG 召回的原子记忆注入格式为 `- [type][importance=0.85] 内容`，不带 role_scope 标签，模型看不出是角色专属还是 shared。

**影响：**

模型无法区分记忆归属。如果需要模型按角色归属做不同处理（比如"这是 Alice 专属偏好 vs 通用偏好"），当前格式不够。

**潜在方案：**

在 `formatRagMemories` 里加 role_scope 标签，如 `- [fact][id:alice-001][importance=0.85] 内容`。shared 时不带标签。

**改动成本：**

- 代码改动 2 处（chatCompletions 映射 + formatRagMemories）
- verify-assembler 177 个测试快照需更新
- 缓存无影响（dynamic block 不缓存）

**相关文件：**

- `src/assembler/blocks.ts` — `formatRagMemories`（314-326 行）
- `src/api/chatCompletions.ts` — recallHitsAsMemories 映射（126-155 行）

## 3. 做梦时 shared 原子记忆无法自动更新

**状态：** 接受现状，待观察

**问题：**

`ROLE_MEMORY_ENABLED=true` 时，做梦只构造非 shared 角色组，没有 shared group。shared 原子记忆无法通过做梦自动整理（合并重复、删除过时）。

**影响：**

- shared 记忆过时/重复时只能靠 MCP 主动更新（`memory_upsert` 不传 role）
- 召回时跨 scope 去重已临时折叠近重复，注入不重复，不影响对话体验
- shared 数据库可能保留旧版本

**接受理由：**

符合设计文档"shared 记忆靠 MCP 主动维护"策略。做梦自动整理 shared 有风险（可能把角色专属信息误写进 shared）。

**如果未来需要处理：**

做梦时如果有无角色消息，构造一个 shared group 处理 shared 记忆的更新/删除。

**相关文件：**

- `src/memory/dailyDigest.ts` — 角色分组逻辑（1257-1265 行）、applyDreamV2 的 scope 校验（997-1029 行）

## 4. baseline pending 机制尚未实现

**状态：** 方案已确认，待实施

**问题：**

baseline 目前只能由做梦自动生成/更新，没有 MCP 工具让模型主动提交 baseline 的小幅增删改。

**已确认的最终规则：**

1. baseline 只能由 `baseline_change` pending 修改
2. 普通 dream 不得根据聊天自行修改 baseline
3. baseline pending 独立处理，不随消息分批重复处理
4. 每晚每个有 pending 的角色只合并、写入一次
5. 没有 pending 就不调用 baseline 模型
6. 模型生成和数据库写入都成功后，才能标记 applied；失败则保留 pending 下次重试
7. MCP 校验：
   - add：必须有 after
   - update：必须有 before + after
   - delete：必须有 before
   - role_id 和 reason 不能为空
   - 不允许 shared baseline

**待实施内容：**

- 新建 `baseline_changelog` 表
- 新增 MCP `baseline_change` 工具
- 做梦流程去掉 baseline 自动生成，新增 `applyBaselineChanges` 独立处理
- 对话注入 baseline pending（复用 pending_changes 路径，加 before_content + reason）
- 屏蔽 `memory_change_add/update/delete`（从 getTools 注释掉）
- 新角色首版 baseline：模型看到 `<long_term_baselines>` 为空时主动提交首版 pending

- `src/api/mcp.ts`（新增工具 + 注释旧工具）

- `src/api/chatCompletions.ts`（查 baseline_changelog 拼入 pending）
- `src/assembler/types.ts`（PendingChange 加 before_content）
