# 多角色记忆系统设计说明补充

> 本文档追踪多角色记忆系统的设计理念与变更原因，供后续开发接手时理解"为什么这样设计"。  
> 与 `缓存与记忆改造方案.md`（前一轮改造）和 `角色记忆实施方案.md`（执行细则）互补：那两份讲"怎么做"，本文讲"为什么这么做"以及"以后改之前要记得什么"。

---

## 目标范围

当前系统目标不是实现一个完全自动化的人格记忆系统，而是提供：

1. 稳定的角色连续性
2. 低噪声的长期记忆维护
3. 高相关度的记忆召回
4. 稳定的缓存利用

系统优先保证可控性和可维护性，不追求自动生成大量记忆。

---

## 当前记忆分层设计

### 1. 角色长期印象（Role Baseline）

用途：
记录当前角色长期形成的"如何理解用户"的信息。

例如：
- 用户偏好
- 用户行为模式
- 长期关系状态
- 角色与用户互动方式

特点：
- 低频更新（每晚做梦时生成/继承，不随单次对话频繁变化）
- 当前角色专属（请求只注入当前角色 baseline，不合并 shared/其他角色）
- 进入稳定缓存区域
- 不应该因为短期聊天频繁变化

设计原因：
角色连续性主要依赖稳定认知，而不是大量历史事实。把"角色怎么看用户"和"发生过什么具体事"分开，避免 baseline 被一次性安排或临时语气污染。

> ⚠️ 后续改动注意：如果要让 baseline 反映更频繁的变化，需重新评估缓存稳定性影响 — baseline 在 boot 包里属于稳定区，频繁变动会破坏缓存命中。

### 2. 最近互动日记（Daily Log）

用途：
记录近期角色与用户发生的重要互动。

特点：
- 按角色归属（namespace + role_scope + date 唯一）
- 当前角色读取最近两天
- 用于补充近期上下文
- 不替代长期记忆
- 同日分批时合并：非首批读取已有日记喂入 prompt，模型输出合并版完整 daily_log

设计原因：
短期事件不应该污染长期记忆，但需要让新窗口知道最近发生了什么。日记和 baseline 分层让"近期发生了什么"和"角色长期怎么看用户"互不干扰。

> ⚠️ 后续改动注意：日记写入有白名单校验（只允许本次实际构建的 roleGroups 中的 scope），模型凭空生成不存在的角色日记会被丢弃。如果放宽这个限制，要确认不会污染其他角色注入。

### 3. 原子长期记忆（Memory）

用途：
保存可被检索的具体事实。

例如：
- 用户明确表达的偏好
- 项目信息
- 历史事件
- 需要长期保留的小细节

特点：
- 支持 embedding 召回
- 支持 rerank
- 支持角色 scope（role_scope 字段隔离）
- 支持 MCP 主动维护
- 跨 scope 去重只在注入时临时折叠，不删数据库记录

设计原因：
不是所有信息都适合写入角色印象，需要保留可检索的细粒度信息。召回时跨 scope 去重优先级为 当前角色 > shared > 其他角色，保留数据库完整性优先于注入效率。

> ⚠️ 后续改动注意：存储去重只在同一 role_scope 内进行，禁止跨角色删除或 mark-seen。如果未来要支持跨角色合并，需设计显式合并流程而非自动合并。

## 自动提取策略（运行策略，非废弃）

### 当前状态

自动提取默认关闭（`ENABLE_AUTO_MEMORY=false`）。

### 定位

**自动提取是"已实现但当前关闭的运行策略"，不是废弃功能。** 代码完整保留，不删除，避免影响已有数据链路。未来如果重新启用，无需重新开发。

### 关闭原因

自动提取适合高频聊天用户，但当前使用场景更依赖 MCP 主动维护。

自动提取存在风险：
- 容易产生大量低价值记忆
- 重复记忆增加召回噪音
- 模型推断可能被误认为事实
- 角色归属难判断
- 增加维护和去重成本

因此当前采用：模型主动调用 MCP 写入重要记忆。

### 重新启用前需评估

- 记忆质量过滤（置信度阈值、最低 importance）
- 角色归属判定（从消息继承 vs 显式标注）
- 人工审核流程（是否走 pending changelog）
- 去重策略（自动提取产生的记忆与 MCP 写入的记忆如何去重）
- 频率控制（每 N 条消息提取一次，避免每轮都跑）

> ⚠️ 这个项目最值钱的不是自动提取，而是"记忆怎么进入上下文"这条链已经打通。自动提取只是记忆来源之一，关闭它不影响召回/注入/baseline/日记等下游链路。

## 缓存设计原则

缓存优先级高于实时完整性。

结构（从上到下，上方越稳定）：
```
System
Tool definitions
角色长期印象 baseline
稳定摘要
历史上下文
当前消息
动态召回记忆
```

设计原因：
长期稳定内容应该尽量保持缓存命中。频繁变化的内容（当前消息、临时召回、pending 变化）放在动态区域，避免影响前面缓存。

> ⚠️ 后续改动注意：baseline 和 daily_log 在 boot 包里属于稳定区。如果让它们随每轮对话实时更新，会破坏缓存命中。当前设计是 baseline/日记只在做梦时更新，请求时只读不写。

## 召回设计原则

召回流程：
```
粗召回 → rerank → 相关性排序 → role boost（后置） → 跨 scope 去重 → 注入上下文
```

设计原因：
向量相似度只能提供候选，不代表真正相关。rerank 用于进一步判断当前问题是否需要该记忆、记忆是否重复、记忆重要程度。

### role boost 后置

role boost 只在 reranker 之后应用，不前移。

设计原因：
pre-boost 在 reranker 前加权，会被 reranker 重新打分覆盖，导致 boost 数学上失效。后置才能让 boost 真正影响最终排序。

> ⚠️ 后续改动注意：如果要把 boost 前移，需确认 reranker 不会覆盖 boost 信号，否则 boost 等于没生效。

### 跨 scope 去重

召回阶段允许临时合并重复内容，减少上下文长度。优先级：当前角色 > shared > 其他角色。Jaccard ≥ 0.7 才折叠，短内容（<6 token）跳过避免误判。

原因：数据库保存完整性优先，注入效率其次。被折叠的命中只在本次注入结果中剔除，不删除数据库记录。

## 去重原则

存储去重：按 namespace + role_scope 隔离。

原因：不同角色可能拥有相似但独立的记忆。例如 Alice "用户喜欢猫" 和 Bob "用户喜欢猫" 不能因为文本相同删除其中一个。

召回去重：临时折叠，不删数据库记录（见上节）。

> ⚠️ 后续改动注意：如果未来要支持"跨角色事实合并"，需设计显式合并流程（例如 MCP 工具或 admin 面板操作），不能自动合并。

## 角色身份规则

优先使用 role_id。

原因：角色名称可能修改，role_id 是稳定角色卡 ID。

规则：
- role_id 存在：scope = `id:<role_id>`
- 无 role_id 有 role_name：scope = `name:<role_name>`
- 无角色：scope = `shared`

role_name 主要用于展示和兼容。

### Operit 角色标记解析

Operit 无法修改请求顶层字段，通过独立插件注入 SYSTEM 标记：
```xml
<aelios_role_context>
{"role_id":"稳定角色卡ID","role_name":"当前角色名称"}
</aelios_role_context>
```

解析规则：
- body 顶层 role_id/role_name 优先，仅当顶层缺字段才用标记值
- 只解析独立 SYSTEM message（string content，只含标记块）
- 严格 JSON + 字段白名单 + ≤200 字符长度限制
- 多标记拒绝全部回退顶层
- 残缺/解析失败/超长/未知字段一律删标记 + warn，不转发上游
- 标记不得出现在：上游/数据库/dream/五轮历史/assembler/日志

设计原因：角色改名但 ID 不变时仍使用同一个 `id:<role_id>` scope，保证记忆连续性。顶层优先让前端有能力显式覆盖标记。

> ⚠️ 后续改动注意：如果放宽标记解析（例如允许 user 消息中的标记），要确认不会让用户消息伪造角色身份。当前严格只认独立 SYSTEM。

## 做梦（Dream）流程设计

### pending 前移

pending changelog 在做梦模型调用前应用，让模型看到刚应用的变更状态。

设计原因：如果 pending 在做梦后才应用，模型基于旧状态生成整理计划，可能与实际状态冲突。

### 角色分组

按 computeRoleScope 分组，每个角色组只处理该角色窗口内的 user + assistant 消息。shared memories 作为只读参考，不可在角色组中修改。

超过 DREAM_MAX_ROLES_PER_RUN 时直接失败不推进 cursor，不静默丢弃角色。

### 重复 target 阻止

同一 target_id 在一次 dream 中出现多次操作（update+delete 或重复 update）视为冲突，全部跳过不执行。

设计原因：dream 模型输出异常时不应造成数据丢失。两个操作都不执行比"选一个执行"更安全。

> ⚠️ 后续改动注意：如果要让冲突操作走 admin 审核（memory_changelog conflict），需确认 dream 流程和 changelog 流程是独立的，不要把 dream 输出异常写入 changelog conflict。

## 暂不扩展内容

以下功能暂不实现：
- 自动人格推断
- 自动大量记忆生成
- 跨角色记忆合并
- 复杂权限系统
- 自动删除历史记忆
- 每角色独立模型调用

原因：当前目标是稳定连续性，而不是构建完整自主记忆代理。

> 这些是"暂不"不是"永不"。如果未来要扩展，先评估是否影响当前缓存稳定性/角色隔离/召回质量。

---

## 维护原则

优先修复：
- 数据丢失
- 角色串记忆
- 缓存失效
- 无法恢复的数据状态

避免：
- 大规模重构
- 删除已有能力
- 为未来需求提前设计复杂系统

## 后续开发追踪点

以下是改动时容易踩坑的地方，记录在此避免遗忘：

1. **migration 0006 只能跑一次** — D1 ALTER TABLE 不支持 IF NOT EXISTS，重复执行会报错。部署前必须备份。
2. **daily_log 重建有数据丢失风险** — 0006 含 DROP TABLE + RENAME，D1 不支持事务，中断会丢数据。
3. **Vectorize metadata 需回填** — 部署后跑 `backfill-vectorize-role.mjs`，未回填的视为 shared。
4. **前端需传 role_id** — 否则所有记忆落共享区。Operit 通过 `<aelios_role_context>` 标记传。
5. **ROLE_MEMORY_ENABLED 语义** — false 时仍保存 role_id + fact_key 隔离，但不启用角色行为。开关只控制服务端是否启用角色层行为，客户端始终应传 role_id/role_name。
6. **update/delete 归属从目标记忆继承** — MCP schema 不接受 role 参数，角色归属由目标记忆决定。
7. **role boost 只后置** — reranker 后应用，前移会被覆盖。
8. **pending 注入查 shared + 当前角色并集** — 不只查当前角色，共享 pending 也要注入。
9. **同日分批日记合并** — 非首批读已有 daily_log 喂入 prompt，模型输出合并版。如果改成"每批独立写"，会丢失前批内容。
10. **写入白名单** — daily_log/baseline 写入时用本次实际构建的 roleGroups 的 scope 过滤，模型凭空生成的角色组不写入。
11. **重复 target 真正阻止** — 两阶段统计 op 次数，>1 全部跳过。不是只 warn。
12. **Operit 标记残缺也删除** — 闭合缺失的标记不转发上游，避免泄露协议细节给模型。
13. **wrangler d1 本地验证** — 用临时 toml 指向本地 D1 真实执行 migration，不要只靠单元测试 mock。
